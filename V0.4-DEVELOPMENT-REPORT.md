# BC Sentinel v0.4.0 Beta — Development Report

## Executive summary

v0.4 implements the roadmap's **Reputation + Network Intelligence** phase on top of the v0.3.1 RC1 adversarial-hardened baseline. Existing scanning, real-time protection, ransomware detection, quarantine, ETW attribution and Premium UI behavior were preserved.

The release creates a local, explainable bridge between process identity, file reputation and outbound connection telemetry without pretending that user-space observation is a firewall or kernel EDR.

## 1. Baseline and regression gate

Baseline: `BC_Sentinel_v0_3_1_RC1_Adversarial_Hardened.zip`.

Before changes: **137/137 tests passed**.

After v0.4: **152/152 tests passed**.

## 2. File reputation changes

The reputation engine now records first-seen and distinct-path prevalence per SHA-256. Repeated warm scans do not inflate prevalence or rewrite a database observation for every file.

Authenticode inspection now captures:

- status;
- status message;
- signer subject / publisher;
- issuer;
- thumbprint;
- certificate validity window;
- timestamp signer.

The old `(status, publisher)` wrapper remains for compatibility.

Reputation remains context rather than an unconditional bypass. Valid signing can dampen weak heuristics but does not negate deterministic signatures. Publisher allowlisting is accepted only after Windows reports a valid signature.

## 3. Network intelligence engine

New module: `sentinel/network_intelligence.py`.

It provides:

- normalized IP/domain indicators;
- local address classification;
- local endpoint reputation verdicts;
- endpoint first-seen;
- connection and process prevalence;
- explainable score deltas;
- false-positive profiles for high-volume legitimate network clients;
- a raw-indicator-minimizing optional provider interface.

Ordinary Internet access receives no risk solely for being Internet access. Stronger context is required, such as known-malicious local reputation, risky interpreter behavior, selected administrative ports, or an unsigned/unknown process running from a risky temporary location.

## 4. Network false-positive controls

Weak repeated-connection and recent-file-write correlations are suppressed for common browser/launcher/sync/developer clients. Known-malicious endpoint reputation is not suppressed by those profiles.

This specifically prevents cache-writing browsers or developer tools from accumulating weak network evidence into a false user-facing alert.

## 5. Telemetry Service integration

`TelemetryBroker` now owns a `NetworkMonitor`, but network collection starts disabled after service restart. The authenticated UI explicitly enables or disables collection based on the user's setting.

When service network telemetry is active:

1. the local UI network collector is stopped;
2. process/network data share the service ProcessTree;
3. network events are returned through the existing authenticated localhost protocol;
4. endpoint reputation enrichment is performed in the polling worker rather than the Qt main thread;
5. the UI performs behavioral correlation;
6. persistence is batched.

If the service is unavailable, the local psutil monitor remains the fallback.

## 6. Database changes

Additive schema changes include:

- certificate context columns on `file_reputation`;
- `file_observations`;
- `endpoint_reputation`;
- `network_endpoint_observations`;
- network event columns for endpoint reputation and process identity;
- `record_telemetry_batch()` for one-transaction service persistence.

A migration regression test covers a representative v0.3.1 schema.

## 7. Performance work

A first synthetic network benchmark produced roughly **509 events/s**. Profiling showed redundant endpoint-reputation SQLite reads and avoidable service/UI transaction overhead.

Optimizations:

- 30-second bounded local endpoint-verdict cache;
- worker-thread reputation enrichment for service events;
- batch persistence for service telemetry;
- distinct-placement file prevalence rather than repeated scan observations.

Final synthetic network benchmark, 5,000 events / 250 endpoints / 25 processes:

- elapsed: **4.686 s**;
- throughput: **~1,067 events/s**;
- events persisted: **5,000/5,000**;
- max correlated synthetic score: **84**;
- external lookups: **0**.

Final 5,000-file benchmark:

- cold: **1.498 s / ~3,338 files/s**;
- warm: **1.160 s / ~4,312 files/s**;
- warm hash-cache hits: **4,950/5,000**;
- executable/script cache bypass remains intentional.

The real-time benchmark in this Linux container still uses the documented direct-pipeline fallback because native watchdog is unavailable here.

## 8. UI integration

The existing Premium UI was not redesigned. Small integration changes expose the new data:

- Protection page status for Network Intelligence and File Reputation;
- updated settings explanations;
- Activity detail endpoint reputation/prevalence/process signature context;
- threat detail Authenticode and first-seen/prevalence context.

## 9. Acceptance tooling

`tools/windows_acceptance.py` now also creates a harmless localhost TCP connection and verifies that the native network collector attributes it to the current process and classifies the endpoint as loopback.

Required Windows freeze gate:

```powershell
python -m tools.windows_acceptance --benchmark-files 5000 --realtime-seconds 3 --output acceptance-v040.json
```

Native acceptance should verify:

- ETW process/file providers;
- watchdog Observer;
- Authenticode;
- NTFS reparse/junction handling;
- timestamp-restoration evasion protection;
- psutil process→connection attribution;
- local network reputation enrichment;
- CPU/RAM/I/O under realistic Windows workloads.

## 10. Security and product limits

v0.4 does **not** block packets and does not claim WFP/driver-level enforcement. It does not automatically reverse-resolve IP addresses. External threat intelligence is not enabled.

Hashing an IP is not considered anonymous; the optional provider contract is only a minimization boundary. Production threat-intelligence integration requires a separate privacy/security decision.
