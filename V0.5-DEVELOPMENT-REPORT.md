# BC Sentinel v0.5.0 Beta — Development Report

## 1. Release objective

Build a safe incident-correlation and operator-response layer on top of the already validated v0.4.0 Reputation + Network Intelligence baseline and the v0.4.1 Behavioral Correlation Engine 2.0 prerequisite.

The target was not autonomous remediation. The target was to create a trustworthy incident object, preserve explainability, require explicit operator intent for destructive actions and create a complete audit trail before the future privileged-service phase.

## 2. Baseline evidence

The supplied Windows v0.4.0 acceptance run passed all critical checks, including ETW process/file startup, Authenticode, watchdog, NTFS reparse handling and process→network attribution. The 5,000-file field run reported no critical failures.

The v0.4.1 Behavioral Correlation Engine 2.0 exists as the prerequisite layer in this source tree. A dedicated v0.4.1 native Windows freeze is not claimed; v0.5 must perform its own native acceptance.

## 3. Core implementation

### Incident correlation

Added `sentinel/incident_engine.py`.

The engine:

- consumes normalized `SecurityEvent` telemetry plus Behavioral Correlation 2.0 output;
- reuses the correlation engine's `BCI-*` incident ID when available;
- groups events by PID/process generation or conservative fallbacks;
- preserves a bounded human-readable timeline;
- aggregates process identity, path, hash, signature, signer, categories and reasons;
- keeps only the strongest signal in each evidence family to reduce duplicate score inflation;
- derives score/level/confidence with the existing central scoring primitives;
- suppresses non-deterministic allowlisted context;
- keeps deterministic/high-confidence evidence visible even when heuristic allowlist context exists;
- generates review/quarantine/termination/containment recommendations without executing them.

### Persistence

Extended SQLite with:

- `incidents`;
- `incident_actions`;
- indexes for updated time, score, subject and response audit lookup.

Added database APIs for incident upsert/read/list and response-action recording.

### Manual response foundation

Added `sentinel/response_engine.py`.

`terminate_process` requires:

- explicit `approved=True`;
- score >= 70;
- confidence >= 0.60;
- valid non-system PID;
- no protected critical process name;
- no protected Windows system path;
- no BC Sentinel allowlist match;
- unchanged process creation time when captured;
- matching live executable path when accessible.

The engine sends a graceful terminate only. If the process does not exit before timeout, the result is `partial`; v0.5 never escalates to a forced kill automatically.

`quarantine_file` requires explicit approval, score >= 70, an existing regular non-reparse file, no allowlist match and no protected Windows system path. It delegates to the existing hardened encrypted `QuarantineManager`.

`contain_network` deliberately returns `unsupported`. v0.5 does not create ad-hoc firewall rules before a hardened privileged service exists.

### UI integration

The existing Activity view now:

- displays incident ID/score/confidence/status;
- exposes incident evidence/recommended actions;
- enables manual `Termina processo` / `Quarantena file` controls only for eligible non-suppressed incidents;
- asks for explicit confirmation before response;
- reports the guarded response result to the operator.

The premium design system and existing navigation are preserved.

## 4. Windows acceptance updates

`tools/windows_acceptance.py` now contains:

1. the v0.4.1 Behavioral Correlation Engine 2.0 synthetic chain probe;
2. a new side-effect-free v0.5 incident/response probe that:
   - builds a synthetic incident;
   - verifies the expected incident ID/score;
   - attempts a process response with `approved=False`;
   - requires the action to fail closed;
   - requires the blocked action to be persisted in the audit trail.

The acceptance harness never terminates or quarantines anything during this probe.

Windows conditional dependencies are included in the main package requirements:

- `pywintrace==0.2.0`;
- `pywin32>=311`.

## 5. Validation performed in this environment

- full pytest suite: **176/176 PASS**;
- `python -m compileall -q app sentinel tools`: **PASS**;
- Behavioral Correlation 2.0 synthetic probe: **PASS**;
- v0.5 Incident Response Foundation synthetic probe: **PASS**.
- synthetic incident-persistence benchmark: **5,000 events / 456.06 events/s**, ~3.6 MB RSS delta, see `benchmark_v050_incident.json` (local container benchmark with SQLite persistence; not a Windows ETW benchmark).

The development container does not have PySide6 installed, so a real GUI runtime/visual acceptance was not executed here. The user's Windows v0.4 environment previously reported PySide6 installed; v0.5 still requires a fresh native Windows run.

## 6. What is intentionally NOT claimed

v0.5.0 Beta does not claim:

- autonomous remediation;
- production tamper resistance;
- service-owned response authority;
- WFP/kernel network filtering;
- pre-execution blocking guarantees;
- signed production installer/updater;
- cloud reputation service;
- macOS protection parity.

These omissions are deliberate security boundaries, not hidden failures.

## 7. Native Windows freeze procedure

From an elevated PowerShell in the v0.5 project directory:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m tools.windows_acceptance --benchmark-files 5000 --realtime-seconds 3 --output acceptance-v050-final.json
```

Freeze criteria:

- all tests PASS;
- `passed: true`;
- `critical_failures: []`;
- ETW process/file PASS;
- network process attribution PASS;
- behavioral-correlation-v2 PASS;
- incident-response-foundation PASS.
